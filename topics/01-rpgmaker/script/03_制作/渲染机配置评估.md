# 渲染机配置评估

> 对象：阿里云 ECS（Windows Server 2022）· Qoder + Remotion
> 评估日期：2026-10-21

---

## 一句话结论

**这台机器做 2D 动画没问题，做 3D 不行，做 4 分钟长片会很吃力。**

Remotion 链路已经跑通（hello.mp4 验证过），这部分不用动。问题集中在三处：没有 GPU、磁盘只剩 18.7 GB、CPU 只有 2 核。

---

## 二、五个问题，按严重程度排

### P0 · 没有 GPU，Blender 这条路走不通

配置里写的是「AspDod / AspIdd 虚拟显示适配器，无独立显存，无 GPU 加速」。

这意味着：

- Blender 的 **Eevee 渲染器直接不可用**（它要 OpenGL）
- 只能用 **Cycles CPU 渲染**，而 Cycles 在 2 核 4 线程上渲染一帧 1080p 可能要 5–15 分钟
- 一个 5 秒的 3D 镜头 = 150 帧 = **12 小时以上**

**另外，这台机器的软件清单里没有 Blender。** 你之前说"下一台电脑有 blender + mcp"，但这份文档里只有 Node / Remotion / Chrome / FFmpeg / Python / AE / Maya。

这两件事需要你确认：Blender 到底装没装？Blender MCP 能不能连上？

### P0 · 磁盘只剩 18.7 GB，长片会爆盘

C 盘剩 58.5 GB，D 盘剩 **18.7 GB**。

如果按"渲染 PNG 序列再拼接"的方式做 4 分钟视频：

```
7574 帧 × 约 2.5 MB/帧 ≈ 19 GB
```

**刚好把 D 盘撑爆。**

必须改成：直接输出 h264，不落 PNG 序列。Remotion 支持边渲染边编码，这样中间文件只有几百 MB。

### P1 · 2 核 4 线程，4 分钟片子渲染时间会很长

| 画面复杂度 | 渲染速度 | 7574 帧需要 |
|---|---|---|
| 简单（文字、色块、淡入淡出） | 3–5 帧/秒 | 25–42 分钟 |
| 中等（粒子、模糊、多层合成） | 1–2 帧/秒 | 1–2 小时 |
| 复杂（WebGL、大量 SVG 滤镜） | 0.3–0.8 帧/秒 | 2.6–7 小时 |

**这不是不能做，是要有心理准备。** 而且渲染期间机器基本干不了别的。

### P1 · Windows Server 可能缺中文字体

Windows Server 2022 默认不一定装全套中文字体。如果 Remotion 里用了系统没有的字体，渲染出来是方块。

而且 `@remotion/google-fonts` 需要访问 Google，这台机器在国内网络环境，大概率拉不下来。

**必须做的事**：把字体文件（.ttf / .woff2）直接放进项目 `public/fonts/`，用 `staticFile()` 引用。不依赖系统字体，也不依赖网络。

### P2 · AE 和 Maya 装了，但基本用不上

- AE 在无 GPU 的服务器上，预览和渲染都极慢
- Maya 的 Viewport 2.0 需要 GPU，2 核 CPU 跑 Arnold 渲染同样不现实
- 而且这两个软件 AI 没法直接控制（不像 Remotion 是纯代码）

**它们占的是磁盘，不是产能。** 如果 D 盘紧张，可以考虑卸掉。

## 三、针对这台机器的调整方案

### 1. 3D 改在本地做，导出素材上传

```
本地机器（有 GPU）
  └── Blender 渲染 3D 镜头 → MP4（带透明通道用 ProRes 4444 或 PNG 序列）
        ↓ 上传
渲染机
  └── Remotion 里用 <OffthreadVideo> 或 <Img> 当素材用
```

这样渲染机只负责 2D 合成，压力小一个量级。

### 2. 渲染命令必须改

```bash
# 不要这样（会生成几万张 PNG，撑爆磁盘）
npx remotion render Main out/ --image-format=png

# 要这样（直接编码，中间文件很少）
npx remotion render Main "../../输出文件夹/xxx.mp4" \
  --codec=h264 \
  --concurrency=1 \
  --crf=18
```

`--concurrency=1`：2 核开并发只会互相抢，反而更慢。

### 3. 长片必须分段

```
第 1 段 0:00–0:45  →  渲染  →  检查  →  删除中间文件
第 2 段 0:45–1:30  →  渲染  →  检查  →  删除中间文件
...
最后 ffmpeg concat 成整片
```

Remotion 支持用 `<Sequence>` 只渲染某个区间（`--frames=0-1350`），配合脚本可以自动化。

### 4. 字体本地化

```tsx
import { staticFile } from "remotion";

const font = new FontFace(
  "SourceHanSans",
  `url(${staticFile("fonts/SourceHanSansSC-Regular.otf")})`
);
```

字体文件放 `public/fonts/`，不要用 Google Fonts。

### 5. 单条时长控制在 90 秒以内

文档里写的"建议规格：1080p / 30fps，单条 10–90 秒"是诚实的。这台机器做 4 分钟不是不行，但要把渲染时间算进项目周期。

## 四、和上一份清单的冲突（需要你拍板）

我在 `千本樱MV_技术栈复刻清单.md` 里写的是"Blender + MCP 做 3D"。**这个方案在这台机器上不成立。**

三条路，你选一条：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 放弃 3D** | 全片用 Remotion 做 2D / 2.5D（CSS 3D transform、伪透视） | 视觉上少一层，但这条片子本来 3D 占比就不高 |
| **B. 本地渲 3D，上传素材** | 本地 Blender 出片，渲染机只做合成 | 需要两台机器之间传文件，流程多一步 |
| **C. 换机器** | 换一台有 GPU 的 | 成本最高，但如果要做千本樱那种量级，这是唯一解 |

**我的建议是 B。** 你本来就有本地 Blender，3D 镜头数量不多（机械恐龙、MSX 机器那几个），本地渲完传上去就行。

## 五、需要你确认的三件事

1. **Blender 到底在不在这台机器上？** 软件清单里没有，但你说有。
2. **这台机器能不能上外网？** npm 镜像指向 npmmirror，说明至少能访问国内。这决定了字体和依赖怎么装。
3. **文案怎么传过去？** 现在是两台机器，需要一个固定的交接方式（网盘 / 共享目录 / 复制粘贴）。

## 七、Blender 跑通之后的三个问题

> 2026-10-21 18:25 更新。清单新增：Blender 5.2.2 LTS（`D:\blender`）、MCP 扩展 1.0.3（9876 端口）、MMD Tools、`blender_test.mp4`（1.33 秒 / 320×180 / 12fps）。

### 问题一：这个测试的规格，说明不了产能

`blender_test.mp4` 是 320×180、12fps、1.33 秒。换算一下：

| 维度 | 测试 | 真实需求 | 倍率 |
|---|---|---|---|
| 像素 | 320×180 = 57,600 | 1920×1080 = 2,073,600 | **36×** |
| 帧率 | 12 fps | 30 fps | 2.5× |
| 5 秒镜头帧数 | 16 帧 | 150 帧 | 9.4× |

**计算量差约 340 倍。**

按 Cycles 在 2 核 CPU 上的常见表现（1080p / 64 采样 / 简单场景，约 30–60 秒一帧）估算：

```
5 秒 3D 镜头（150 帧）= 75–150 分钟
30 秒 3D 总量（900 帧）= 7.5–15 小时
```

**这不是"不能做"，是"要提前排期"。** 那条片子里 3D 镜头建议控制在 **30 秒以内**，而且要放在最后渲——晚上挂机。

### 问题二：PNG 序列会吃光 D 盘

清单里写的是「PNG 序列 → ffmpeg 合成 MP4」，这是对的（这个 5.2 构建不支持直接出 MP4）。

但 PNG 太大了：

```
1080p PNG ≈ 2–3 MB/帧
4 分钟 = 7200 帧 ≈ 14–22 GB
D 盘剩余 18.7 GB
```

**刚好卡在爆盘线上。**

三个改法，任选：

| 方案 | 做法 | 效果 |
|---|---|---|
| **换 JPEG** | 输出格式改 JPEG，质量 95 | 一帧 300–500 KB，7200 帧约 2–3.6 GB |
| **分段** | 每 30 秒渲一段，合成后立刻删序列 | 峰值占用降到 2 GB 以内 |
| **降分辨率** | 720p 渲染，后期放大 | 空间减半，但画质有损 |

推荐 **JPEG + 分段**，两个一起用。

### 问题三：MMD + Cycles CPU 是双重负担

MMD Tools 启用是好事，千本樱那种 MV 确实要用初音模型。但要知道成本：

- MMD 模型面数通常 2–5 万，比普通场景高一个量级
- MMD 的 toon 材质 + 球面贴图，转 Cycles 要重新调，否则发灰
- 无 GPU 时，Cycles 处理高面数模型 + 复杂材质，渲染时间会再翻几倍

**结论：MMD 可以导入、可以摆姿势、可以做单帧截图。但用它渲 4 分钟动画，这台机器不现实。**

如果一定要做千本樱那种，只有两条路：
1. 本地有显卡的机器渲
2. 换一台带 GPU 的云服务器（按小时计费，渲完就关）

### 还有一个隐患：Blender 5.2 的 API

Blender 5.x 是大版本，Python API 有 breaking changes。清单里同时存在 4.5（"不使用、不修改"）和 5.2，两个版本的插件不共享。

这意味着：
- AI 生成的 bpy 脚本，可能是按 4.x 的写法
- 网上大部分教程是 4.x 的
- MCP 扩展 1.0.3 是否完全兼容 5.2，需要实测

**建议：只留 5.2，把 4.5 卸掉或移走。** 两个版本并存，后面一定会在"为什么这个脚本在另一台上跑不了"上浪费时间。

### 下一步该测什么

不要再测"能不能跑"，测"跑多快"。

```bash
# 一个 1080p 单帧，看要多少秒
blender -b scene.blend -o //test_#### -F PNG -f 1
```

记下三个数：
1. **单帧耗时**（秒）
2. **单帧 PNG 大小**（MB）
3. **峰值内存占用**

这三个数一出来，整条片子的 3D 预算就能算了。
